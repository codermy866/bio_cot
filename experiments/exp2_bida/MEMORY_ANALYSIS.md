# 显存占用分析报告

## 问题现象
- GPU 1显存占用只有326MB（0.7%），非常少
- 训练卡在第一个batch，没有真正开始

## 原因分析

### 1. 模型参数量小
- **模型总参数量**: 5,985,415 (约600万)
- **模型参数显存**: 22.83 MB (float32)
- **激活显存估算**: 1.88 MB (batch_size=64)
- **总显存估算**: 24.71 MB

**结论**: Bio-COT模型本身非常轻量级，参数量只有600万，所以显存占用很少。

### 2. 训练卡在第一个batch
从日志看：
```
Training:   0%|          | 0/11 [00:00<?, ?it/s]
```

**可能原因**:
1. 数据加载慢（OCT图像处理耗时）
2. 第一个batch的前向传播卡住（可能是Sinkhorn OT计算）
3. 数据加载器阻塞

### 3. 显存占用低的具体原因

#### 3.1 模型轻量级
- Student Prior: 7 → 256 → 512 → 768 (约50万参数)
- Dual Head Encoder: 512 → 1536 → 768 (约200万参数)
- Classifier: 768 → 768 → 384 → 2 (约100万参数)
- Center Discriminator: 768 → 5 (约4000参数)
- Memory Bank: 只是buffer，不占用太多显存

**总参数量**: 约600万，显存占用约23MB

#### 3.2 数据特征已经提取
- 使用的是预提取的特征（`oct_features`, `colposcopy_features`）
- 不是原始图像，所以显存占用少
- 每个样本的特征大小: 512维（float32 = 2KB）

#### 3.3 Batch Size = 64
- 每个batch的特征显存: 64 × 512 × 4 bytes × 2 (OCT + Colpo) = 262KB
- 激活显存: 64 × 768 × 4 bytes × 多层 ≈ 2-3MB

### 4. 为什么训练卡住？

**可能原因**:
1. **数据加载慢**: OCT图像处理需要时间
2. **Sinkhorn OT计算**: 第一个batch的Sinkhorn迭代可能很慢
3. **Memory Bank初始化**: 第一次更新Memory Bank可能有问题

## 解决方案

### 方案1: 检查数据加载
- 确认数据加载器是否正常工作
- 检查第一个batch的数据是否正确

### 方案2: 添加调试信息
- 在第一个batch添加详细的日志
- 检查每个步骤的耗时

### 方案3: 优化Sinkhorn OT
- 如果Sinkhorn OT太慢，可以：
  - 减少max_iter
  - 增大eps（加快收敛）
  - 使用更简单的距离度量（如MSE）作为fallback

### 方案4: 检查Memory Bank
- 确认Memory Bank的更新逻辑是否正确
- 检查是否有死锁或阻塞

## 预期显存占用

如果训练正常进行：
- **模型参数**: ~23 MB
- **激活值**: ~5-10 MB (batch_size=64)
- **优化器状态**: ~50 MB (AdamW需要保存momentum)
- **梯度**: ~23 MB
- **数据缓存**: ~5-10 MB
- **总计**: ~100-120 MB

**当前326MB是合理的**，因为：
- 可能包含了PyTorch的CUDA上下文
- 可能包含了数据加载器的缓存
- 可能包含了其他进程的显存占用

## 结论

**显存占用少是正常的**，因为：
1. 模型本身很轻量级（600万参数）
2. 使用的是预提取的特征，不是原始图像
3. Batch size=64，激活显存不大

**真正的问题是训练卡在第一个batch**，需要：
1. 检查数据加载是否正常
2. 检查Sinkhorn OT计算是否卡住
3. 添加调试信息定位问题
